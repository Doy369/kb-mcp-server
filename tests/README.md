# tests/ — 自动化测试（260 例，离线零服务依赖）

```bash
python -m pytest tests/ -q      # 260 passed，本地约 12s
```

不装 torch、不联网、不需要任何外部服务（dev 嵌入 + memory 后端跑全部断言）。
CI 的 `test` job 会额外装 `psycopg[binary]` / `pgvector` 这两个**轻量客户端库**
（无服务、无 torch），以便单测覆盖存储层真实的类型注册路径；真实 Postgres 的
端到端验证由 `pg` job 负责，真实 MCP 协议验证由 `mcp` job 负责（`scripts/check_mcp.py`）。

## 设计取舍：为什么 CI 里跑 dev 而不跑 bge

CI 在 dev 嵌入下评测失败是**预期行为**，不是本目录引入的问题。

实测数据（见 ROADMAP 基线指标表）：

| 嵌入 | 语义断言前 | 语义断言后 | 说明 |
|---|---|---|---|
| dev（离线零依赖，CI 默认） | 82%（9/11） | **91%（10/11）** | P2 哨兵用例 FAIL |
| bge（本地模型） | 100%（11/11） | **100%（11/11）** | 全通过 |

唯一 FAIL 仍是「P2 问题多久响应」——dev 哈希嵌入对 `P0/P1/P2` 这类**字面高度相似**的片段
区分不了，排序近乎随机，会误命中 15 分钟。**这不是回归，是已知的嵌入能力边界。**

因此 CI 用 `0.72` 阈值（而非 100%）作为「不许变差」的护栏，
bge 的 100% 基线由本地或带模型的 job 单独验证。

### 设计取舍：为什么不在 CI 里装 sentence-transformers

- 依赖 torch，镜像数 GB，一次 CI 拉取 + 加载 1.3GB 模型要数分钟；
- 单测已覆盖固定逻辑；评测的语义质量本就该在**换嵌入时**（低频变更）本地验证。

→ **CI 保「快」与「不许变差」，bge 保「质量上限」，两者职责分离。**
