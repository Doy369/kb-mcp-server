# tests/ — 自动化测试（271 例，离线零服务依赖）

```bash
python -m pytest tests/ -q      # 271 passed，本地约 12s
```

不装 torch、不联网、不需要任何外部服务（dev 嵌入 + memory 后端跑全部断言）。
CI 的 `test` job 会额外装 `psycopg[binary]` / `pgvector` 这两个**轻量客户端库**
（无服务、无 torch），以便单测覆盖存储层真实的类型注册路径；真实 Postgres 的
端到端验证由 `pg` job 负责，真实 MCP 协议验证由 `mcp` job 负责（`scripts/check_mcp.py`），
真实并发 HTTP 压测由 `load` job 负责，真实 Apache AGE 图侧由 `age` job 负责，
真实 bge 嵌入由 `bge` job（夜间 + 手动）负责。

> `test_baseline_gate.py` 存在的理由值得单独说一句：CI 脚本过去没有测试，

> 只是不再拦任何东西。共享逻辑要有测试，脚本也不例外。

## 设计取舍：为什么快口径跑 dev、慢口径跑 bge

CI 在 dev 嵌入下评测失败是**预期行为**，不是本目录引入的问题。

实测数据（见 ROADMAP 基线指标表）：

| 嵌入 | 语义断言前 | 语义断言后 | 说明 |
|---|---|---|---|
| dev（离线零依赖，CI 推送时默认） | 82%（9/11） | **91%（10/11）** | P2 哨兵用例 FAIL |
| bge（本地模型） | 100%（11/11） | **100%（11/11）** | 全通过 |

唯一 FAIL 仍是「P2 问题多久响应」——dev 哈希嵌入对 `P0/P1/P2` 这类**字面高度相似**的片段
区分不了，排序近乎随机，会误命中 15 分钟。**这不是回归，是已知的嵌入能力边界。**

### 两种口径怎么并存（P2-10 补）

| | 触发 | 嵌入 | 阈值 | 报告 | 目的 |
|---|---|---|---|---|---|
| `test` job | 每次推送 / PR | dev | **0.72** | `eval_report.json` | 保「**不许变差**」（几秒级） |
| `bge` job | **夜间 03:00 + 手动** | bge（torch + 1.3GB 模型） | **0.95** | `eval_report_bge.json` | 保「**质量上限**」（数分钟级） |

两者**共用 `scripts/check_baseline.py`**，只通过 `KB_BASELINE_MIN` 与报告路径区分——
避免两处阈值各写一套、日久漂移。阈值贴着实测值会让 CI 噪音化进而被忽略，故都留了余量。

**为什么 bge 不跟每次推送**：装 torch + 下 1.3GB 模型会让单次 CI 从 ~40s 涨到数分钟。
高频 job 一旦变慢就会被习惯性忽略，那比没有更糟。所以把它放到**夜间**（并用
`actions/cache` 缓存模型），既保住质量上限这条线，又不拖慢日常反馈。
